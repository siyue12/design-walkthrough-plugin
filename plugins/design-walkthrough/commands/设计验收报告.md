$ARGUMENTS

使用 `design-walkthrough` 技能 §9「设计走查报告（飞书文档）」执行。这是走查登记后的最后一个节点：只读飞书问题登记表，在飞书新建文档交付，**不生成 `.md` 报告文件**。

硬性要求：

- 读 `config/feishu.json` 的 `baseToken` / `tableId` / `baseUrl` / `fieldNames`；报告列名按现场读取的 fields API 顺序，不写死、不照抄其他项目。
- 用 `lark-cli` 翻页拉全量记录（默认 `--as bot`），先保存 `.walkthrough/reports/<日期>-<project>-registry.json` 原始快照，报告数字只从快照计算。
- 排除「问题标题」以「【示例】」「[示例]」开头的记录，并在报告中注明排除数量。
- 用户给了版本/批次就按该值筛选；没给默认全表，报告筛选条件写「全表」。筛选后 0 条则停止并说明。
- 按 `templates/走查报告模版.md` 组织正文，所有 `【】` 替换完，删除「使用说明」区块；正文只在内存/标准输入中使用，不落 `.md`。
- 文档标题默认 `<项目名>走查报告`（如「三号机走查报告」）；用户指定标题就用用户的。
- 用 `lark-cli docs +create --title "<标题>" --doc-format markdown --content - --as user` 创建文档；用户给了文件夹才加 `--parent-token`；从返回取 `data.document.url` / `document_id`。
- 结论按 §9.3 推导：有未关闭 P0/P1 → 不通过；P2/P3 遗留必须同时有负责人、计划修复日期和用户明确提供的批准记录，才可有条件通过；无任何遗留才通过；数据不全退回。不得为了让结论好看而放宽。
- 批准人、日期、责任人、完成时间不能编造；缺失写「无」/「—」/「待排期」。
- 生成后自检：各等级合计 = 记录数，已关闭 + 遗留 = 记录数，5.2 行数 = 记录数。
- 不写回问题登记表、不改记录状态、不建表；给用户飞书文档链接、文档 ID 和快照路径，不要给本地 `.md` 路径。
