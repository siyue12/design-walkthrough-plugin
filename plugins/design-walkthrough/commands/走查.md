$ARGUMENTS

使用 `design-walkthrough` 技能完成本次走查。先确认 Figma 页面/Frame、前端 URL、版本/批次；缺什么问什么，不要猜。先读 Figma 生成设计基线，再逐条到前端取实现值，差集才是问题；基线缺失时先问用户补充规则，补不了才转「待确认项」。全程只走查布局和交互逻辑，业务字段以实际前端页面为准。问题先给人工审核，确认后才允许写入飞书表。

硬性要求：

- 基线只来自当次 Figma 节点树/截图/交互说明；不拿历史走查记录、通用清单、其他系统标准当验收依据。
- 基线没定义的规则不判缺陷；先问用户补充，用户也补不了才登记到「待确认项」表。
- 每条问题必须带 `baselineRef`（B 编号 + node id）。
- 不自动写入飞书表；必须用户明确确认后，才执行 `register-walkthrough.mjs --yes`。
- 每个问题点都要有独立红框截图，截取当前存在差异的前端页面；不要用 Figma 稿、元素小图或一张图框多个问题点代替。
- 多个问题可合并登记在一行，但仅限同一组件/模块或逻辑相关的问题；A 模块和 B 模块的无关联问题不能合并。每个问题点仍各配一张截图；合并后「现象」点与截图按顺序一一对应，最多 3 点（即不超过 3 张图）。
- 走查地址默认按测试环境处理；提交、保存、删除、发布、启用停用、审批等写操作直接执行并记录结果，不需要逐项确认，不能只开到弹窗。
- 用户明确说是生产环境时，退回只读，不执行任何写操作。
- 写操作只限走查地址同源页面；可操作既有测试数据；能撤销的撤销，不能撤销的在结果里列明。
- 截图不需要脱敏（测试环境是脏数据/非生产数据）；表单填什么都可以，非生产环境无影响。
- 前端页面打不开或需要登录时，停在登录页并让用户在受控浏览器里登录，或让用户提供截图；不要动用户自己的 Chrome 标签页。
