# 设计走查登记

把当次 Figma 设计稿/交互说明当作**唯一验收基线**，逐条到前端页面取实现值，差集才是问题；设计稿本身没定义的规则不判缺陷，转入「待确认项」。

## 核心原则

1. **基线只来自当次 Figma**：节点树、截图、交互说明/批注。不来自历史走查记录、通用清单、其他系统的验收标准。
2. **清单不是验收项**：下面的维度只是一组「向实现取值」的提问角度；基线没定义的角度不构成问题。
3. **差集才是问题**：基线条目的设计值 vs 前端实现值；没有设计值就没有偏差，只有待确认。
4. **缺规则先问人**：基线缺失时先让用户补充交互规则；用户也补不了，才登记为待确认项。

## 0. 前置检查

1. **飞书 CLI**
   ```bash
   LARK="$HOME/.zcode/tools/lark-cli/node_modules/.bin/lark-cli"
   PLUGIN_ROOT="${CLAUDE_PLUGIN_ROOT}"
   BASE_TOKEN=$(jq -r '.feishu.baseToken // empty' "$PLUGIN_ROOT/config/feishu.json")
   TABLE_ID=$(jq -r '.feishu.tableId // empty' "$PLUGIN_ROOT/config/feishu.json")
   "$LARK" auth status
   if [ -n "$BASE_TOKEN" ]; then "$LARK" base +table-list --base-token "$BASE_TOKEN"; fi
   ```
   - `auth status` 里 `identities.user.available` 必须为 true。
   - 如果 `needs_refresh`，调用一次 base 命令会自动刷新；失败则运行 `"$LARK" auth login`，把 QR/链接给用户扫码。
   - 主表：以 `config/feishu.json` 的 `feishu.baseToken` / `feishu.tableId` 为准；每个项目配置自己的走查表，插件不写死任何 Base/Table。
   - **新项目允许 `baseToken` / `tableId` 为空**：不阻塞走查，登记阶段（§7）会自动新建 Base/表并回填配置。
   - 表存在时读取字段：用 `lark-cli api GET /open-apis/bitable/v1/apps/<baseToken>/tables/<tableId>/fields --params '{"page_size":100}'`，按 `data.items[].field_name` 记录表头顺序；后续「问题登记清单」按该顺序输出。表不存在时先按 `templates/registry-base-fields.json` 的 17 列顺序输出，建表后再以实时字段为准。
   - 待确认表：同 Base 的「待确认项」，表名和字段 schema 定义在 `config/feishu.json` 的 `feishu.pending`；不存在时由脚本按该 schema 创建。

2. **Figma**
   - 用 Figma MCP：`mcp__figma-local__get_metadata` / `mcp__figma-local__get_screenshot`。
   - 没有明确页面/Frame 时先问用户，不要猜。
   - 走查阶段不需要 `get_design_context`；只有要生成代码时才加载 `figma-design-to-code`。

3. **浏览器**
   - 先加载 `browser-use:control-browser` 技能，按它的 bootstrap 初始化。
   - 优先用 ZCode 内置浏览器（IAB）；内网页面如登录/证书问题，让用户在 IAB 里登录，或让用户提供截图。
   - **不要关闭、重开或操作用户自己的 Chrome 标签页**；不要把用户踢下线。

4. **输入**
   缺少以下任一项就问：
   - Figma 页面/Frame（名称或 node id）
   - 前端 URL
   - 环境属性：默认按**测试环境**处理，测试环境内的写操作直接执行，不需要逐项确认；用户明确说是生产环境时退回只读
   - 版本/批次（默认 `v1.0 走查第1轮`）
   - 走查范围（页面/模块；默认当前页面）

## 1. 建立设计基线

基线是本次走查唯一的验收依据。没有基线值的内容，一律不判缺陷。

### 1.1 读取 Figma

1. 对目标 Frame 调 `get_metadata`，拿到节点树、尺寸、文案、组件、状态。
2. 对目标 Frame 调 `get_screenshot`，看整体布局和状态。
3. 如果 Figma 里有「流程設計」「交互说明」「批注」页面或文字节点，一并读取；交互说明以文字节点/批注为准。
4. 记录页面尺寸（例如 1440×900）。
5. **只看布局和交互逻辑**；不要拿 Figma 里的业务字段去要求前端保持一致，业务字段以前端页面为准。

### 1.2 生成基线条目

把设计稿里**可验证**的内容逐条编号：

| 编号 | 条目 | 设计值/规则 | 来源 |
|---|---|---|---|
| B01 | 顶部 Tab 数量与顺序 | 2 个：HOME、列表；顺序 HOME → 列表 | node 12:34 |
| B02 | 搜索框 | 宽 320px，右侧有清除按钮；无结果时展示空态文案「暂无结果」 | node 12:40 + 说明文字 |
| B03 | 卡片网格 | 4 列，间距 16px；窄屏按 4/3/2 列折行 | node 12:50 |

规则：

- **每条必须能回答「前端应该是什么」**：数值、文案、顺序、数量、状态、行为。
- 粒度到元素/规则级，不拆到单个像素，除非设计稿明确标了数值或规范。
- 来源必须可追溯：node id，或说明文字/批注的原文位置。
- 上表只是格式示例，实际条目必须来自当次 Figma，禁止套用任何预置清单。

### 1.3 基线自检

逐条问自己：这条规则前端能不能被验证？答不出来的，说明设计稿没有定义，标为**基线缺失**，不要凭经验补一个「应该」的值。

### 1.4 基线缺失：先问用户

发现基线缺失时，不要直接判缺陷、也不要把猜测写成期望。**一次性列出全部缺失规则，让用户统一补充或确认无需定义，不要分批询问。**

```text
以下规则设计稿没有定义，需要你补充（或确认无需定义）：
1. 搜索无结果时的空态文案和展示方式？
2. 折叠区块默认展开还是收起？
3. 窄屏下网格按几列折行？
...
```

- 用户补充了规则 → 新增/更新 B 条目，来源写「用户补充 <日期>」，继续取实现值。
- 用户也无法确定 → 记入待确认项，见 §4。

## 2. 打开前端页面并取实现值

1. 用 browser-use 打开用户给的 URL。
2. `tab.setViewportSize({ width: 1440, height: 900 })`；宽度与 Figma Frame 对齐（Figma 不是 1440 时用 Figma 宽度），高度固定 900。
3. `waitForLoadState({ state: "domcontentloaded" })`，必要时等 1~2 秒让 SPA 渲染。
4. 先 `domSnapshot()` 理解结构；需要视觉判断时再 `screenshot()`。
5. 如果页面需要登录：
   - 让用户在 IAB 里完成登录；登录后继续。
   - 如果 IAB 打不开内网/证书错误，停止并让用户提供截图或可登录的测试环境。
   - 不要复制用户 Chrome 的 cookie/token，也不要读取用户浏览器存储。
6. 确认环境：用户提供的走查地址默认视为**测试环境**，提交/保存/删除/发布等写操作直接执行，不需要逐项征求用户确认。若用户明确说是生产环境、页面跳转到与本任务无关的外部真实系统，停止写操作，按只读模式走查。

### 2.1 逐条取实现值

对基线表里的每个 B 条目，到页面上取对应的实现值：

- 数量、顺序、文案：DOM 文本和节点顺序
- 尺寸、间距、对齐、溢出：`getBoundingClientRect()` / `getComputedStyle()` / 截图
- 状态与交互：实际触发 hover / focus / 搜索 / 展开收起 / 弹窗 / 提交，记录实际反馈
- 记录取值的证据：选择器、操作路径、截图

### 2.2 操作覆盖（取值动作，不是验收项）

取值时按以下方面把页面走一遍；**它们只是提问角度，是否算问题仍由基线条目决定**：

#### 布局

- 页面整体尺寸、内容区宽度、左右留白
- 顶部导航：顺序、数量、名称、换行、截断、图标
- Tab：顺序、选中态、关闭按钮、内容对应关系
- 搜索区：位置、宽度、占位符、图标、清除按钮
- 区块/分组：标题、计数、顺序、高度、间距
- 按钮/卡片网格：列数、宽度、间距、文字截断、最后一行对齐
- 内容溢出：横向滚动、纵向滚动、被裁切、遮挡
- 响应式：浏览器宽度变化时是否折行/溢出（至少看 1440 和当前窗口宽度）
- 空状态/加载态/错误态

#### 交互

- Tab 切换是否正常，选中态是否明显
- 搜索：输入、过滤、计数、空结果、清除、匹配规则
- 折叠/展开：默认状态、箭头、点击区域
- hover / focus-visible / disabled / loading
- 弹窗/抽屉：打开、关闭、遮罩、Esc、焦点
- 返回/面包屑/滚动位置

#### 写操作（测试环境）

走查地址默认按测试环境处理，提交/保存/删除/发布/启用停用等写操作要实际点完并记录结果，不能只开到弹窗：

- 表单提交：空必填、错误提示、边界值、重复提交、提交中 loading、成功/失败反馈、成功后列表/详情是否同步
- 取消/重置/返回：是否清空、是否误提交、是否残留脏数据
- 删除：入口、二次确认文案、取消删除、确认删除后的列表/计数/空态/关联数据
- 发布/下架/启用/停用：确认弹窗、操作后状态、前台/列表是否同步、能否撤回
- 审批/驳回（如页面有）：按钮状态、意见是否必填、操作后流转状态
- 每个写操作记录：入口路径、操作前状态、执行的动作、实际结果、是否符合设计/交互说明

边界：

- 测试环境内不需要逐项确认：提交、保存、删除、发布、启停、审批等直接执行并记录结果。
- 只操作走查地址同源页面；不跳到与本任务无关的外部真实系统。
- 可操作页面既有测试数据，也可新建数据；能撤销的操作做完撤销，不能撤销的在输出里列明。
- 表单可填任意内容，测试环境无影响，不用为填数据犹豫。
- 页面提示会触发短信、邮件、扣费、外部系统调用时，按测试环境处理，直接执行并记录。

#### 不计入问题

- 业务字段名称、业务数据、接口字段、权限差异
- 文案业务含义（简繁混用、错别字、截断仅在基线有对应规则时才算问题）
- 纯主观审美偏好（不登记）

## 3. 差集判定

把基线和实现值并排，逐条判定：

| 编号 | 基线条目 | 设计值 | 实现值 | 判定 | 证据 |
|---|---|---|---|---|---|
| B01 | 顶部 Tab 数量与顺序 | 2 个：HOME、列表 | HOME、列表、设置 3 个 | 偏差 | node 12:34；截图 |
| B02 | 搜索无结果空态 | 文案「暂无结果」 | 未验证（设计稿无空态规则） | 待确认 | 说明文字位置 |

三种判定：

- **一致**：实现值等于设计值，不写草稿。
- **偏差**：基线条目有明确值，实现值不同 → 写进 `issues`，必须带 B 编号。
- **待确认**：设计稿没有定义，或实现值取不到（登录/环境限制）→ 写进 `pending`，**不判缺陷、不进主表**。

### 3.1 判定规则

1. 只有基线条目存在明确值时，才能判偏差。
2. 不得用通用经验、历史走查记录、其他系统标准反推基线。
3. 一条问题对应一个基线条目；同一元素多个偏差可合并，但必须列出全部 B 编号。
4. 问题描述的「期望」段只能引用基线条目或用户补充规则；找不到依据就转待确认。

## 4. 待确认项

待确认项是「设计稿缺规则，导致无法判定」的登记，不是缺陷。

每个待确认项记录：

- `title`：缺了什么规则（一句话）
- `module`：页面/模块
- `missingRule`：具体缺失的规则
- `impact`：影响哪些验收点
- `baselineRef`：Figma 节点或说明位置；用户补充过但仍不足的，写明
- `notes`：询问记录（问过谁、结论）

流程：

1. 先按 §1.4 问用户补充规则。
2. 用户补充 → 回填基线，继续走查，不进待确认。
3. 用户也无法确定 → 进 `pending`，审核时单独列出。
4. 用户确认后，与 `issues` 一起写入飞书「待确认项」表。

## 5. 截图与红框标注

**每个问题点都要有一张红框截图：截取当前存在差异的前端页面，并用红框标出该问题点。**

- 截图对象是前端页面当前状态，不是 Figma 稿，也不是脱离上下文的元素小图。
- 默认一个登记问题一张图；同一页面有多个问题时可分别登记，也可合并到一行登记。
- **合并条件**：只有同一组件/同一模块下的问题，或存在明确逻辑关联（同一操作链路、同一根因）的问题才能合并；A 模块 + B 模块这种无关联问题不能登记在同一行。
- **合并登记**：合并后每个问题点仍各配一张截图，不能一张图里框多个问题点；截图按「现象」1/2/3 的顺序一一对应，合并的问题点不超过 3 个。
- 截图范围包含问题点及上下文（所属卡片、列表行、弹窗、区块），能看出问题在页面中的位置；整页布局问题截当前视口或整页。
- 先切到能复现差异的状态（默认态/搜索态/弹窗/操作结果等），再截图。

命名：

```text
.walkthrough/shots/<YYYY-MM-DD>/<page-slug>-<nn>-<issue-slug>.png
```

截图方式：

1. 先把页面切到差异出现的状态；问题在视口外时先滚动到可见。
2. 用 `playwright.evaluate` 拿到问题元素的 `getBoundingClientRect()`。
3. 注入一个临时红色描边层（`position: fixed`、`border: 3px solid #ff4d4f`、`pointer-events: none`、高 z-index），框住问题元素/区域；必要时加一个短标签（如「间距不一致」），截图后移除。
4. 用 `tab.screenshot({ clip: { x, y, width, height } })` 截取问题区域及上下文；clip 在元素 rect 基础上向外留约 40~120px，具体视页面密度调整。
5. 保存：
   ```js
   const { writeFileSync, mkdirSync } = await import("node:fs");
   mkdirSync(dir, { recursive: true });
   writeFileSync(path, Buffer.from(await tab.screenshot({ clip })));
   ```

**写操作取证**：

- 写操作类问题同样每个问题点一张图：截取能看出差异的那一帧（通常是操作结果、报错提示或状态变化），红框框住异常结果。
- 入口、二次确认、操作前状态如需说明，写进 `notes` / 问题描述，不额外占用截图。

**脱敏**：

- 不需要。走查地址是测试环境，页面数据都是脏数据/非生产数据，直接截当前页面即可，不要为了遮数据降低问题可读性。
- 表单填什么都可以，非生产环境无影响。

## 6. 生成草稿并人工审核

把问题和待确认项写成 `.walkthrough/reports/<YYYY-MM-DD>-<page-slug>-draft.json`：

```json
{
  "issues": [
    {
      "title": "顶部 Tab 比基线多 1 个",
      "module": "列表页 / 顶部导航",
      "baselineRef": "B01 / node 12:34",
      "types": ["视觉还原"],
      "severity": "P2",
      "description": "现象：\n1. 基线 B01 定义 2 个 Tab（HOME、列表），实际渲染 3 个，多出「设置」。\n\n期望：\n1. 按 B01 隐藏或移除「设置」Tab。",
      "version": "v1.0 走查第1轮",
      "notes": "B01 / node 12:34；前端选择器 .top-tabs",
      "screenshots": ["/绝对路径/.walkthrough/shots/2026-11-10/list-01-extra-tab.png"]
    }
  ],
  "pending": [
    {
      "title": "卡片 hover 态未定义",
      "module": "列表页 / 卡片",
      "missingRule": "设计稿未定义卡片 hover 时的阴影、位移或描边变化。",
      "impact": "hover 态无法判定是否还原。",
      "baselineRef": "node 12:50（卡片网格）",
      "version": "v1.0 走查第1轮",
      "notes": "已询问用户 2026-11-10，用户也无法确定",
      "screenshots": []
    }
  ]
}
```

### 问题描述格式（必须）

写入飞书「问题描述」前，必须整理成固定两段：

```text
现象：
1. XXXXXXX
2. XXXXXXX
3. XXXXXXX

期望：
1. XXXXXXX
2. XXXXXXX
3. XXXXXXX
```

规则：

- `现象：` 写实际看到的问题、影响、复现路径；1~3 点；必须能对应到 B 编号。
- 写操作类问题：「现象」按「操作路径 + 操作前状态 + 实际结果」写，「期望」写对应基线条目/交互说明要求的行为。
- 空一行，再写 `期望：` 写应该怎样、修复建议、验收标准；1~3 点；只能引用基线或用户补充规则。
- 每点一个核心事实；单点建议 ≤60 字，最多 100 字。
- 不要写长段落、不要重复背景、不要把 Figma 和前端的所有细节都抄进去。
- 脚本会自动重排成这个格式：去掉原有编号/项目符号，超长内容截断；但语义提炼仍由你完成。
- 如果只给了一串要点、没有「现象/期望」分段，脚本会把「建议/应该/补齐/调整」类要点分到期望段，并补一个默认期望；尽量自己写清楚两段。

示例：

```text
现象：
1. 基线 B01 定义 2 个 Tab，实际渲染 3 个，多出「设置」。
2. 多出的 Tab 没有对应内容区，点击后内容区空白。

期望：
1. 按 B01 隐藏或移除「设置」Tab。
2. Tab 顺序恢复为 HOME → 列表。
```

字段规则：

- `title`：一句话，能独立看懂；不要写「样式问题」这种空话。
- `module`：页面/模块，例如 `列表页 / 搜索态`。
- `baselineRef`：必填，写 B 编号 + node id；这是问题成立的前提。
- `types`：`视觉还原` / `交互体验` / `文案` / `功能缺陷` / `兼容适配` / `性能` / `其他`，可多选。
- `severity`：`P0` / `P1` / `P2` / `P3`；按下面「严重程度判定」定级，脚本会映射成 `P0-致命` 等。
- `description`：必须包含「现象：」和「期望：」两段，每段 1~3 个序号要点；不要写长段落。
- `notes`：放 Figma node、前端选择器、设计注释等证据。
- `screenshots`：本地绝对路径；每个问题点一张红框截图。合并登记时按「现象」点顺序放多张，最多 3 张，与点一一对应；没有截图的问题先不要提交。
- `解决方案截图`：由用户人工上传方案图，插件不写入、不覆盖。
- 合并登记仅限同一组件/模块或逻辑相关的问题；`title` 写共性问题，`module` 写共同模块（跨模块流程写共同操作链路）；`description` 的每个现象点对应一张截图，超过 3 个问题点就拆成多条登记。

### 严重程度判定

只对**已确认的基线偏差**定级；基线缺失或取不到实现值 → 转「待确认」，不定级。

按两个维度判断：

1. **交互规则实现**：设计稿/交互说明中的规则是否实现，以及偏差对操作的影响。
2. **影响范围**：受影响的功能范围、用户范围，以及是否有替代路径。

| 影响范围 | 关键交互规则未实现/错误（主流程阻断或结果错误） | 非关键交互规则实现偏差（体验受损但可完成） | 仅细节/文案/视觉差异 |
|---|---|---|---|
| 核心流程 / 全量用户 / 无替代路径 | **P0-致命** | **P1-严重** | **P2-一般** |
| 主要路径 / 主要角色 / 需明显绕行 | **P1-严重** | **P2-一般** | **P3-建议** |
| 局部模块 / 特定状态 / 边缘场景 | **P2-一般** | **P3-建议** | **P3-建议** |

判定规则：

- **关键交互规则**：直接影响主任务完成，如提交、保存、删除、发布、查询、审批、支付等。
- **影响范围取最高档**：功能范围、用户范围、替代路径三者中任一达到更高档，就按更高档算。
- 一条记录含多个问题点时，按其中**最高影响**定级。
- **P0 不轻易给**：只有主流程被阻断、关键结果错误或关键数据丢失才给；样式、文案、局部交互偏差不给 P0，最高按 P1 处理。
- 严重程度 ≠ 修复优先级；P1 也可能先修。
- 纯审美偏好未写入设计基线的，不算问题、不定级。

示例：

| 级别 | 示例 |
|---|---|
| P0 | 删除确认弹窗点「取消」仍执行删除，影响所有删除操作 |
| P1 | 搜索计数不随结果更新，用户需自己数结果；主搜索路径需绕行 |
| P2 | 搜索结果少时仍按 6 列左对齐，只影响搜索态局部 |
| P3 | 按钮 hover 色值与设计稿差一档，仅视觉细节 |

待确认项字段：

- `title`：缺了什么规则，一句话。
- `missingRule`：必填，具体缺失内容。
- `impact`：影响哪些验收点。
- `baselineRef`：对应 Figma 节点/说明位置。
- `status`：默认 `待设计补充`，可选 `已补充` / `确认无需定义`。
- `screenshots`：可选。

### 问题登记清单表头（按目标表动态生成）

审核时给用户的「问题登记清单」必须严格按**本次配置表**的实际表头顺序输出，字段名与飞书表一致，不得增删列、重排或改名。插件是通用的，不写死任何表的列顺序。

- 顺序来源：每次走查开始时，按 `config/feishu.json` 的 `feishu.baseToken` / `feishu.tableId` 调 `lark-cli api GET /open-apis/bitable/v1/apps/<baseToken>/tables/<tableId>/fields --params '{"page_size":100}'`，取 `data.items[].field_name` 的顺序；`baseToken` / `tableId` 为空或表不存在时，先按 `templates/registry-base-fields.json` 的 17 列顺序输出，登记阶段建表后再以实时字段为准。
- **不要用 `+field-list` 的顺序，它每次返回都不稳定**；也不要照抄其他项目的表头。
- `config/feishu.json` 的 `feishu.fieldOrder` 只是该项目的兜底记录；与实时顺序不一致时，以实时顺序为准并更新配置。默认顺序为：问题标题 → 问题编号 → 版本/批次 → 走查页面/模块 → 问题描述 → 问题截图 → 解决方案截图 → 问题类型 → 严重程度 → 状态 → 提出人 → 提出日期 → 负责人 → 计划修复日期 → 修复说明 → 复验结果 → 备注。
- 未产生值的字段按默认填：`问题编号` = `系统生成`；`提出人` = 当前登录用户；`提出日期` = 今天（YYYY-MM-DD）；`状态` = `待处理`；`负责人` / `计划修复日期` / `解决方案截图` / `修复说明` / `复验结果` = `—`。
- `问题描述` 单元格内用 `<br>` 分行，保持「现象：」「期望：」两段和序号要点，不得压成一段。
- `问题截图` 填本地绝对路径；多张按「现象」点顺序用 `<br>` 分隔。
- `备注` 放 `baselineRef`、Figma node、前端选择器等证据。
- 已登记记录的清单同样按当前表的顺序输出。

问题登记清单（表头 = 本次读取的字段顺序）：

| <字段1> | <字段2> | <字段3> | ... |
|---|---|---|---|

待确认项（字段顺序沿用待确认表）：

| # | 模块 | 缺失的规则 | 影响 | 基线依据 |
|---|---|---|---|---|

明确问用户：**哪些问题要登记、哪些要改优先级/措辞、哪些待确认项要写入**。用户没有明确说「登记/确认」之前，不要执行写入。

## 7. 写入飞书

**时机**：问题清单经人工审核、用户明确说「登记 / 确认写入」之后执行。先确认目标 Base/表，再 dry-run，最后写入；目标表不存在时在登记阶段自动新建。

### 7.1 确认目标 Base 和表

```bash
LARK="$HOME/.zcode/tools/lark-cli/node_modules/.bin/lark-cli"
PLUGIN_ROOT="${CLAUDE_PLUGIN_ROOT}"
BASE_TOKEN=$(jq -r '.feishu.baseToken // empty' "$PLUGIN_ROOT/config/feishu.json")
TABLE_ID=$(jq -r '.feishu.tableId // empty' "$PLUGIN_ROOT/config/feishu.json")
```

1. `baseToken` 为空 → 走 §7.2 新建 Base。
2. 有 `baseToken` → 查 Base：

   ```bash
   "$LARK" base +base-get --base-token "$BASE_TOKEN" --as user
   ```

   - 返回正常 → 进入第 3 步。
   - 404 / Base 不存在 → 走 §7.2 新建 Base。
   - 403 / 无权限 / `missing_scope` → 停止，把报错原文给用户，先解决授权或换身份；**不要用建新表绕过**。

3. Base 存在 → 列出现有表：

   ```bash
   "$LARK" base +table-list --base-token "$BASE_TOKEN" --as user
   ```

   - `tableId` 在列表里 → 跳 §7.3，继续原登记流程；不要重复建表。
   - `tableId` 不在列表，但存在名为「走查问题登记」的表 → 用该表的 `table_id` 回填配置，跳 §7.3。
   - 没有「走查问题登记」表 → 走 §7.2 在现有 Base 里补表。
   - 表存在但字段不匹配 → 按 dry-run 的字段自检报错修正字段或配置，不要重建表。

### 7.2 目标不存在时新建

字段唯一来源：`templates/registry-base-fields.json`，固定 17 列：问题标题、问题编号、版本/批次、走查页面/模块、问题描述、问题截图、解决方案截图、问题类型、严重程度、状态、提出人、提出日期、负责人、计划修复日期、修复说明、复验结果、备注。不再让用户确认字段清单，也不要求先 dry-run。

先读字段模板：

```bash
FIELDS=$(cat "$PLUGIN_ROOT/templates/registry-base-fields.json")
```

**A. 新建 Base**（`baseToken` 为空或 Base 不存在时）：

```bash
"$LARK" base +base-create \
  --name "<Base名>" \
  --table-name "走查问题登记" \
  --fields "$FIELDS" \
  --folder-token "<folder_token>" \
  --as user
```

- Base 名默认 `<项目名>-设计走查问题登记`；用户没给文件夹时删掉 `--folder-token` 行，落在「我的空间」。
- 默认 `--as user`；只有用户明确要求才用 `--as bot`。
- 从返回取 `app_token`（Base token）和首表 `table_id`；缺 table_id 时用 `base +table-list --base-token "<app_token>" --as user` 查。

**B. 现有 Base 补表**（Base 存在但没有「走查问题登记」表时）：

```bash
"$LARK" base +table-create \
  --base-token "$BASE_TOKEN" \
  --name "走查问题登记" \
  --fields "$FIELDS" \
  --as user
```

**C. 补「待确认项」表**（不存在时；默认建）：

```bash
PENDING_FIELDS=$(jq -c '.feishu.pending.tableFields' "$PLUGIN_ROOT/config/feishu.json")

"$LARK" base +table-create \
  --base-token "<base_token>" \
  --name "待确认项" \
  --fields "$PENDING_FIELDS" \
  --as user
```

- 已存在就跳过；字段 schema 只来自 `config/feishu.json` 的 `feishu.pending.tableFields`。

**D. 回填配置**：

1. 改前备份生效目录的 `config/feishu.json`：
   `cp config/feishu.json config/feishu.json.bak-$(date +%Y%m%d-%H%M%S)`。
2. 只改 `feishu.baseToken` / `feishu.tableId` / `feishu.baseUrl` / `feishu.pending.tableId`。
3. `fieldNames` / `fieldOrder` / `pending.tableFields` 不动；`fieldOrder` 已包含全部 17 个字段。
4. 新 Base 的 URL 从创建返回取；没有就按 `https://<domain>/base/<app_token>` 拼。

完成后继续 §7.3，把本次确认的问题写入目标表；不要停在「表已建好」。

### 7.3 dry-run

```bash
node "$PLUGIN_ROOT/scripts/register-walkthrough.mjs" \
  --input .walkthrough/reports/2026-11-10-list-draft.json \
  --dry-run
```

把将要写入的 payload、截图路径、待确认表结构给用户看。

### 7.4 写入

用户确认后：

```bash
node "$PLUGIN_ROOT/scripts/register-walkthrough.mjs" \
  --input .walkthrough/reports/2026-11-10-list-draft.json \
  --yes
```

- `issues` 写入主表（走查问题登记）。
- `pending` 写入「待确认项」表。
- 脚本会先查重；同名问题默认跳过，确认要重复登记才加 `--allow-duplicate`。
- 创建记录后自动上传截图；上传失败会返回 `recordId` 和 `uploadError`，用同一个 recordId 重试，不要重建记录。
- 返回 `recordId` / `recordUrl` / `upload`，把链接给用户。

只登记用户确认的条目：可以直接编辑 draft JSON，删掉不登记的条目，再执行。

### 7.5 待确认表规则

- 表名、字段 schema 定义在 `config/feishu.json` 的 `feishu.pending`。
- 配置了 `feishu.pending.tableId` 就直接用；没有配置则按表名在 Base 里查找。
- 找不到时：dry-run 只打印将创建的表结构；`--yes` 写入时才用该 schema 建表。
- 也可单独预建：
  ```bash
  node "$PLUGIN_ROOT/scripts/register-walkthrough.mjs" --ensure-pending-table --yes
  ```
  建好后把返回的 `tableId` 回填到 `feishu.pending.tableId`（可选，能加快后续查找）。
- 建表结构只来自插件配置，不读取任何外部文档或历史记录。

## 9. 设计走查报告（飞书文档）

**触发**：用户说「生成设计走查报告」「生成设计验收报告」「出验收报告」「生成验收报告」时执行。这是插件的最后一个节点：走查、登记、修复完成后，读取飞书问题登记表，按 `templates/走查报告模版.md` 组织正文，**在飞书新建一篇文档**交付，不生成 `.md` 报告文件。只读问题登记表，不改记录。

### 9.1 读取问题登记表

1. 读配置：

   ```bash
   LARK="$HOME/.zcode/tools/lark-cli/node_modules/.bin/lark-cli"
   PLUGIN_ROOT="${CLAUDE_PLUGIN_ROOT}"
   BASE_TOKEN=$(jq -r '.feishu.baseToken' "$PLUGIN_ROOT/config/feishu.json")
   TABLE_ID=$(jq -r '.feishu.tableId' "$PLUGIN_ROOT/config/feishu.json")
   ```

   - 主表字段顺序按 `GET /open-apis/bitable/v1/apps/<BASE_TOKEN>/tables/<TABLE_ID>/fields` 的 `data.items[].field_name` 读取；报告列名与表一致，不写死、不照抄其他项目。
   - 表名用 `GET /open-apis/bitable/v1/apps/<BASE_TOKEN>/tables` 匹配 `TABLE_ID` 得到；取不到就写 tableId。

2. 拉全量记录（必须翻页取完）：

   ```bash
   "$LARK" api GET "/open-apis/bitable/v1/apps/$BASE_TOKEN/tables/$TABLE_ID/records" \
     --params '{"page_size":100}' --as bot
   ```

   - 响应 `data.has_more=true` 时，带 `page_token` 继续取，直到 `has_more=false`。
   - 默认用 `--as bot`；bot 读不到再用用户身份。用户身份报 `missing_scope` 时，按报错里的 `verification_url` 让用户授权，授权完成前不要编造数据。
   - 只读接口；不要为了读数据去改表、建字段或写记录。

3. 保存原始快照到快照目录：
   `.walkthrough/reports/<YYYY-MM-DD>-<project-slug>-registry.json`
   内容至少包含 `readAt`、`baseToken`、`tableId`、`filter`、`records`（原始 fields）。报告里的所有数字只从这份快照计算，不手工估算。

4. 筛选：
   - 用户给了版本/批次：只保留「版本/批次」匹配的记录。繁简/大小写不一致时先列出候选值让用户确认，不要自行归并。
   - 用户没给：全表，报告筛选条件写「全表」。
   - **排除示例记录**：`问题标题` 以「【示例】」「[示例]」开头的记录不计入统计，报告注明「已排除示例记录 N 条」。
   - 筛选后 0 条：停止生成，告诉用户没有可统计的记录和当前筛选条件。

5. 待确认项：读 `feishu.pending`（`tableId` 或按 `tableName` 查找）。存在且有记录时，按同一版本/批次筛选后放进 5.3；不存在或为 0 条时写「无。」。待确认项不计缺陷、不参与结论判定。

### 9.2 统计口径

**状态**：

- 已关闭 = `状态` 为 `已关闭`。
- 遗留 = 其余状态（`待处理` / `处理中` / `待验证`）。

**等级**：取 `严重程度` 前缀 `P0` / `P1` / `P2` / `P3`，报告里保留表内原值（如 `P2-一般`）。

**维度映射**（按 `问题类型`）：

| 维度 | 问题类型 |
| --- | --- |
| UI 视觉一致性 | 视觉还原 |
| UE 交互体验 | 交互体验、功能缺陷 |
| 兼容适配 | 兼容适配 |
| 性能与稳定体验 | 性能 |
| 内容与可访问性 | 文案 |
| 问题闭环 | 全部记录 |
| 其他 | 其他（实际出现时才在 5.1 追加该行） |

- 一条记录可含多个问题类型，维度计数会重复；5.1 必须注明「维度计数合计 ≠ 记录数」。
- 5.1 的「结果」：该维度 0 条 → `不适用`；有记录且遗留 0 → `通过`；有遗留 → `发现问题`。「问题闭环」行按全部记录判断。
- 5.2 排序：P0 → P3，同级按问题编号升序；列取报告模版定义并加「飞书记录」链接列。
- 飞书记录链接：`<baseUrl>?table=<tableId>&record=<recordId>`。
- 8.1 占比 = 该维度问题数 / 维度计数合计；保留 1 位小数。

### 9.3 结论判定

按顺序执行，不得为了结论好看而放宽：

1. 读不到表、筛选后无记录、关键字段缺失 → **退回**。
2. 存在未关闭 P0/P1 → **不通过**。
3. 存在遗留 P2/P3：
   - 每条遗留都有 `负责人` 和 `计划修复日期`，且用户明确提供了遗留批准记录（批准人 + 日期）→ **有条件通过**。
   - 缺负责人、缺排期或缺批准记录 → **不通过**，结论摘要写明缺哪项。
4. 无遗留（P0~P3 全部已关闭）→ **通过**。
5. 模版里的「P2 均已评估不影响上线」必须有用户明确结论；没有就按遗留处理，不自行认定。

- 批准人、日期、责任人只能来自表内数据或用户明确提供；没有就写「无」/「—」，不得编造。
- 「检查项完成率」在本插件口径下 = 范围内记录均已登记状态；有记录缺状态字段时按退回处理。

### 9.4 生成飞书文档

1. 读模版：`$PLUGIN_ROOT/templates/走查报告模版.md`。
2. 项目名：取记录「走查页面/模块」的共同首段（按 `/`、`／` 分隔）；取不到或存在多个项目时问用户，不要猜。
3. 版本/批次：用户指定优先；全表时写「全表」。
4. 编制人：默认 `lark-cli auth status` 的当前用户；用户指定优先。
5. 文档标题：默认 `<项目名>走查报告`（例如「三号机走查报告」）；用户指定标题就用用户的。版本/批次写在正文，不塞进标题，除非用户要求。
6. 填写规则：
   - 所有 `【】` 必须替换；无数据填 `—`；删除「使用说明」区块。
   - 报告数字与快照一致；生成后自检：各等级合计 = 记录数，已关闭 + 遗留 = 记录数，5.2 行数 = 记录数。
   - 第七章只列 P0/P1 全部、P2 遗留、以及需带版上线的遗留项；没有时写「无。」。
   - 8.2 原因归类必须带证据（问题类型/模块计数）；只能推断时标注「推测」；证据不足写「数据不足以归类」。
   - 8.3 改进建议的完成时间：用户没给就写「待排期」，不得编日期。
   - **不要保存 `.md` 报告文件**；模版只用于组织正文，最终交付物是飞书文档。
7. 创建飞书文档（正文用 Markdown 从 stdin 传入）：

   ```bash
   "$LARK" docs +create \
     --title "<项目名>走查报告" \
     --doc-format markdown \
     --content - \
     --as user <<'REPORT_EOF'
   <替换后的报告正文>
   REPORT_EOF
   ```

   - 用户给了目标文件夹就加 `--parent-token "<folder_token>"`；没给就放「我的空间」。
   - 默认 `--as user`；只有用户明确要求才用 `--as bot`。
   - 从返回取 `data.document.document_id` / `data.document.url`；`ok=false` 时按报错修正，不要退回生成 `.md`。
   - 只创建一次；失败重试前先确认没有已创建的文档，避免重复建多篇。
8. 生成后给用户统计摘要、结论和飞书文档链接；保留 `registry.json` 原始快照（JSON，不含 `.md` 报告）。**不自动回写问题登记表，不修改记录状态。**

## 10. 硬约束

- **基线唯一来源**：基线只能从当次 Figma 节点树/截图/交互说明生成；禁止把历史走查记录、旧问题清单、其他系统的验收标准当基线。
- **不反推**：基线没写的规则，不得用通用经验补成「应该怎样」，更不得据此判缺陷。
- **缺失先问人**：基线缺失时一次性列出全部缺失规则，让用户统一补充，再决定是否转待确认。
- **待确认不判缺陷**：基线缺失或实现值取不到的内容，只登记到「待确认项」表，不进主表、不定严重程度。
- **每条问题可追溯**：`issues` 必须带 `baselineRef`（B 编号 + node id），否则不允许登记。
- **默认测试环境，直接执行**：用户给的走查地址默认按测试环境处理；提交/保存/删除/发布/启用停用/审批等写操作必须实际执行并记录结果，不需要逐项征求用户确认，也不能只开到弹窗。
- **生产则只读**：用户明确说是生产环境，或页面实际指向与本任务无关的外部真实系统时，不执行任何写操作。
- **写操作有边界**：只操作走查地址同源页面；可操作既有测试数据；能撤销的撤销，不能撤销的在输出里列明。
- **表单随意填**：测试环境非生产，填什么都可以；截图不脱敏，按 §5 直接截当前页面。
- **一问题点一图**：每个问题点都要有独立红框截图，不能一张图框多个点；合并登记时截图与「现象」点按顺序一一对应，最多 3 点。
- **合并登记有限制**：只能合并同一组件/模块或逻辑相关的问题；A 模块与 B 模块的无关联问题必须分开登记。
- **不自动写入**：没有用户明确确认，不允许 `--yes`。
- **问题描述必须两段分点**：`现象：` + `期望：`，每段 1~3 个序号要点；长段落会被脚本截断。
- **不碰业务字段**：业务字段以前端页面为准；只比较布局和交互。
- **不动用户浏览器**：不关闭/重开用户 Chrome 标签页，不读取用户 cookie/localStorage。
- **不猜**：Figma Frame、前端 URL、版本/批次不明确就问。
- **表头不写死**：清单列顺序每次按目标表实时读取（fields API），不照抄模板表或其他项目。
- **字段自检**：`register-walkthrough.mjs` 会读 `+field-list` 校验字段和选项；失败时按报错修正，不要绕过。
- **示例记录**：表里已有 `NO.001` 示例记录，未经确认不删除、不修改。
- **报告只读**：生成设计走查报告只读问题登记表，只新建飞书文档；不写回、不改状态、不删记录、不建表。
- **报告不落 .md**：交付物是飞书文档，不生成 `.md` 报告文件；模版只用于组织正文。
- **统计来自快照**：报告数字只从本次 `registry.json` 快照计算；先落快照再写报告。
- **结论由数据推导**：P0/P1 未关闭 → 不通过；有条件通过必须同时有责任人、排期和批准记录；数据不全 → 退回。
- **报告不编造**：批准人、日期、责任人、完成时间、原因归类都不能凭空补；缺失写「无」/「—」/「待排期」，推断标「推测」。
- **报告排除示例**：`问题标题` 以「【示例】」「[示例]」开头的记录不进统计，并在报告中注明排除数量。
- **建表字段固定**：登记阶段自动建表只能按 `templates/registry-base-fields.json` 的 17 个字段、顺序、类型和选项创建；不得增删、重排或改选项，要改先问用户。
- **建表合并进登记**：不单独跑建表节点；用户确认登记后先检查目标 Base/表，存在就直接写入，不存在才建，建完继续写入本次确认的问题。
- **不重复建表**：只有 `baseToken`/`tableId` 为空或接口明确返回 404/表不存在时才建；403/权限错误先解决授权，不得用建新表绕过。
- **自动建表不确认字段**：建表阶段不 dry-run、不让用户逐项确认字段；只补 Base 名和存放位置，用户没给就用默认值。
- **自动建表默认用户身份**：默认 `--as user`；用 bot 建表必须用户明确同意，并说明落在机器人空间及授权问题。
- **建表不写示例记录**：建表本身只建结构；建完继续 §7.3 写入本次人工确认的问题。
- **配置只改生效目录**：回填 token 前先备份，只改 `baseToken` / `tableId` / `baseUrl` / `pending.tableId`；市场副本保持模板配置。
